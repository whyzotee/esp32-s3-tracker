# Tracker Firmware — TODO และรายการรอทดสอบ

อ้างอิงการตรวจโค้ด ณ วันที่ 15 ตุลาคม 2026 รายการนี้มีเฉพาะสิ่งที่ยังไม่รองรับ ข้อจำกัดที่ต้องตัดสินใจ และสิ่งที่ยังไม่มีผลทดสอบยืนยัน ไม่ได้หมายความว่าทุกรายการเป็นข้อผิดพลาดหรือจำเป็นต้องเพิ่มทั้งหมด

## 1. ความสามารถที่ยังไม่ได้เพิ่ม

- [x] **Low Battery — Firmware:** เข้าเมื่อ ≤15% และกลับปกติเมื่อ ≥20% เก็บสถานะใน RTC ไม่เขียน NVS ส่ง flag bit 5 (`0x20`) โดย payload ยังเป็น 15 ไบต์ ไม่เปลี่ยนรอบส่งหรือ Event SOS/Fall อัปเดต decoder ใน README และเพิ่ม host test แล้ว
  - [ ] **ทดสอบ Low Battery บนบอร์ด:** ตรวจ threshold ขาลง/ขาขึ้น สถานะข้าม Deep Sleep และค่าที่ Server decode โดยใช้แหล่งจ่ายที่ปลอดภัยตามวงจร ไม่คายประจุแบตต่ำเกินข้อกำหนด
  - [ ] **Application Alert:** นำ `flags.low_battery` ไปแจ้งเตือนเฉพาะตอนเข้าสถานะแบตต่ำ ไม่แจ้งซ้ำทุก uplink และไม่ตีความค่า `null` จาก ADC invalid ว่าแบตกลับปกติ
- [ ] **Movement Detection:** ตัดสินใจว่าต้องใช้หรือไม่ หากใช้ ให้กำหนดเงื่อนไขและเพิ่มสถานะเคลื่อนไหว ปัจจุบันยังไม่มี Logic นี้
- [ ] **Stationary Detection:** ตัดสินใจว่าต้องใช้หรือไม่ หากใช้ ให้กำหนดเวลานิ่งและเงื่อนไขสร้าง Event การตรวจ Free-fall ปัจจุบันไม่ใช่การตรวจอยู่นิ่ง
- [ ] **Vibration Motor:** ตัดสินใจว่าต้องใช้หรือไม่ ปัจจุบันมีประกาศขาแต่ยังไม่มี Pattern การสั่น

## 2. ข้อจำกัดที่ต้องตัดสินใจและออกแบบ

- [ ] **ยืนยันการส่ง SOS/Fall ถึงเครือข่าย:** ปัจจุบันเป็น unconfirmed uplink การส่งสำเร็จทางวิทยุไม่ได้ยืนยันว่า Gateway/Server ได้รับจริง ให้พิจารณา confirmed uplink หรือ application ACK พร้อมขอบเขต Retry และผลต่อพลังงาน ทั้งนี้ LoRaWAN ACK ไม่ได้ยืนยันว่า Web Platform สร้าง Alert สำเร็จ
- [ ] **Pending SOS/Fall เมื่อ Gateway ปิด:** ปัจจุบันเก็บส่งใหม่เมื่อ Device ตรวจพบข้อผิดพลาด แต่ล้าง Event เมื่อ `sendReceive()` คืนค่าไม่ติดลบ แม้ปลายทางอาจไม่ได้รับ ต้องกำหนดเกณฑ์สำเร็จให้สอดคล้องกับวิธียืนยันการส่ง
- [ ] **Pending Event หลังไฟดับ/Reset:** Event เก็บใน RTC และอาจสูญหายเมื่อไฟดับหรือ Reset บางประเภท ให้กำหนดว่าต้องเก็บข้ามเหตุการณ์เหล่านี้หรือไม่ โดยคำนึงถึงจำนวนครั้งที่เขียน Flash
- [ ] **SOS Location เมื่อไม่เคยมี Fix:** ปัจจุบันอาจส่ง `0,0` ได้ ให้กำหนดการแสดงสถานะไม่มีพิกัดฝั่ง Application และนโยบายว่าจะส่งพิกัดตามหลังหรือไม่ โดยไม่ทำให้ SOS แรกล่าช้า
- [ ] **ลำดับ SOS และ Fall ที่ค้างพร้อมกัน:** ปัจจุบันเลือก Fall ก่อน ให้ยืนยันลำดับที่ต้องการ และทดสอบว่าส่งครบทั้งสอง Event
- [ ] **Last Known Position และ Low Power หลังไฟดับ:** ปัจจุบันเก็บใน RTC เพื่อข้าม Deep Sleep ไม่รับประกันหลังถอดแบต ให้ยืนยันว่าข้อจำกัดนี้ยอมรับได้หรือจำเป็นต้องเพิ่มการเก็บถาวร

## 3. ทดสอบยืนยันบนอุปกรณ์จริง

- [ ] **หลังปรับ SPI ลดกระแส:** แม้วัด Deep Sleep ได้ประมาณ 90 µA แล้ว ให้ทดสอบตื่นจาก Timer และส่ง LoRa ต่อเนื่องหลายรอบ ตรวจ Session Restore และ Frame Counter
- [ ] **SOS Wake หลังปรับ SPI:** กด SOS ระหว่าง Deep Sleep ตรวจว่าตื่น ส่งสถานะ SOS และกลับไปหลับได้
- [ ] **Fall Wake หลังปรับ SPI:** ใช้อุปกรณ์รองรับแรงกระแทกจำลอง Free-fall ระหว่าง Deep Sleep ตรวจการปลุก เสียง และ Fall Payload โดยไม่ทดสอบให้คนล้มจริง
- [ ] **Backend Receive:** ตรวจข้อมูลตั้งแต่ ChirpStack ผ่าน Integration/API จนถึง Backend ไม่ใช่ตรวจเพียงผลส่งจาก Device
- [ ] **SOS Delivery:** ตรวจว่า Web Platform แสดง Alert/Incident ถูกอุปกรณ์และถูก Event รวมถึงการรับ Event ซ้ำ
- [ ] **การชาร์จ:** ตรวจวงจรชาร์จและการทำงานจริงตามข้อกำหนดของแบตเตอรี่และวงจร
- [ ] **สถานะการชาร์จ:** ตรวจ LED/Charger ในแต่ละสถานะ ปัจจุบัน Firmware ไม่ได้อ่านสถานะชาร์จเข้ามา
- [ ] **Power Rail 3.3 V:** วัดขณะ Boot, เปิด GNSS, ส่ง LoRa และตื่นจาก Sleep เพื่อยืนยันแรงดัน โดยเฉพาะจังหวะโหลดเปลี่ยน
- [ ] **แรงดันและเปอร์เซ็นต์แบต:** วัดเทียบมิเตอร์หลายระดับแรงดัน รวมช่วงชาร์จและช่วงมีโหลด เปอร์เซ็นต์ปัจจุบันเป็นค่าประมาณจากแรงดัน
- [ ] **Watchdog / Unexpected Reset:** ทดสอบการกลับมาทำงานและความถูกต้องของ Session/Nonce/Pending Event หลังจำลอง Fault และ Reset อย่างควบคุมได้ ปัจจุบันยังไม่มีผลยืนยันครบทุกกรณี

## การบันทึกผล

เมื่อทำแต่ละข้อเสร็จ ให้ติ๊กช่องและบันทึก Firmware Version, เงื่อนไขทดสอบ, ผลที่ได้ และ Commit ที่เกี่ยวข้องไว้ใต้ข้อนั้น รายการที่ตัดสินใจไม่ทำ ให้ระบุเหตุผลแทนการติ๊กว่าเสร็จ
